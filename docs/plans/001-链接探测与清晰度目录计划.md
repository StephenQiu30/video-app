# Plan 001：链接探测与清晰度目录

## 1. 交付边界

本地用户阅读支持范围、粘贴 URL、确认处理权并提交。浏览器经同源 BFF 调用已冻结的 server OpenAPI，恢复 Resolution/SSE，展示 canonical 错误或媒体信息与真实清晰度，并把选中的 opaque `format_key` 锁定在 query state。

本 Plan 不把 key 提交给下载接口，不创建下载，不展示第三方缩略图、假进度、AI、思维导图或 PDF。后续能力只以准确路线说明出现。

## 2. 前置门禁

- Web Design 001–003 与 PRD 001 为 `accepted`，本 Acceptance 为 `accepted/result: pending`。
- Server Plan 001 已 `done`，其 Acceptance 全部 passed。
- `video-server/openapi/openapi.json` 已提交、可重复生成且 SHA-256 记录在本 Acceptance；禁止以手写平行 fixture 绕过依赖。

## 3. TDD 实施任务

### 3.1 工程与 Red

- [ ] 建立锁定的 Next.js 16.2、React 19.2、TypeScript、Vitest、Playwright 与 axe 基线。
- [ ] 先写表单/权利、BFF token、幂等、状态/SSE、错误、Variant、恢复和无障碍红灯测试。
- [ ] 建立 lint、typecheck、unit、build、e2e、a11y 和 OpenAPI diff 命令。

### 3.2 App Shell 与本地主体

- [ ] 建立暖纸/深墨 token、字体、reset、响应式容器和减少动画。
- [ ] 实现 Server Component 外壳与最小 Client Component 工作台。
- [ ] Web listener 只绑定 127.0.0.1；BFF 仅放行 5 个 method/path，拒绝 traversal/未来 API；冻结 LOCAL schema、token 和边界 fail closed。

### 3.3 生成契约与幂等

- [ ] 仅从接受的 server OpenAPI 生成 transport types 与 MSW fixture。
- [ ] 实现 snake_case → view model 纯转换、Problem Details 和 request ID。
- [ ] 同一表单快照复用 key；URL/确认变化清空任务、选择并生成新 key。

### 3.4 Resolution 主流程

- [ ] 读取/展示 current rights statement；实现 URL、versioned confirmation、stale refetch/reconfirm、字段错误、提交和按钮防重。
- [ ] 映射 QUEUED/RUNNING/RETRY_WAIT/SUCCEEDED/FAILED 与 canonical stage/code。
- [ ] 实现 fetch-based SSE 与 BigInt decimal cursor、重复/乱序丢弃、3 次退避后 2 秒轮询 Resolution、invalid/reset/终态刷新。
- [ ] 用 `/?resolution={id}&format={key?}` 恢复同一 Resolution，不创建新 Job。

### 3.5 媒体与清晰度

- [ ] 展示标题、来源、时长、policy 和解析/过期时间，不请求第三方缩略图。
- [ ] 逐字段展示 null、estimate、音轨、合并、推荐和格式属性。
- [ ] 桌面使用语义表格 + radio，移动端使用同组规格卡。
- [ ] 本地选择只保存 opaque key，不向不存在的下载接口提交。

### 3.6 验证与收口

- [ ] 覆盖全部 Plan 001 canonical code、Problem envelope 和异步 error。
- [ ] 验证焦点迁移、live region、44px、reduced motion、纯键盘和 WCAG checklist。
- [ ] 验证 375/768/1440 px、200% 缩放、长标题、多语言、null 与错误详情。
- [ ] 按数据分类扫描敏感面；用冻结单一 fixture/reset profile 运行浏览器 click→目录 p95 与 Lighthouse user-flow CWV。
- [ ] 回填 Acceptance；独立 Tester/Reviewer 无 blocker 后才能 done。

## 4. Red / Green 门禁

Red 必须由行为测试失败：false rights 仍发送、token 进入浏览器、URL 变化复用旧 key、SSE 丢事件、刷新新建 Job、错误码漂移、Variant 无键盘语义或 BFF 泄漏请求正文。

Green 必须证明 accepted OpenAPI 的正负 fixture 均准确渲染；同一 Resolution 可刷新/断网恢复；只锁定 opaque key；完整键盘路径、响应式、泄漏扫描与性能验收通过。
