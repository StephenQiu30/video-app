# Plan 001：链接探测与清晰度目录

## 1. 交付边界

已验证邮箱主体阅读支持范围、粘贴 URL、确认处理权并提交。浏览器经同源 Backend for Frontend（BFF）使用 Server 当前 production/loopback profile 的 HttpOnly 会话 Cookie 和签名 double-submit 跨站请求伪造（CSRF）header 调用已冻结的 Server OpenAPI，恢复 Resolution/SSE，展示 canonical 错误或媒体信息与真实清晰度，并把选中的 opaque `format_key` 锁定在 query state。BFF 不向 JavaScript 暴露会话值。

本 Plan 不把 key 提交给下载接口，不创建下载，不展示第三方缩略图、假进度、AI、思维导图或 PDF。后续能力只以准确路线说明出现。

## 2. 前置门禁

- Web Design 001–003 与 PRD 001 为 `accepted`，本 Acceptance 为 `accepted/result: pending`。
- Web Plan 000 已 `done`，Acceptance 002 的邮箱、会话、CSRF、身份与认证契约项全部 `passed`。
- Server 认证基础与来源解析 Plan 均已 `done`，对应 Acceptance 全部 `passed`。
- `video-server/openapi/openapi.json` 已同时冻结 accepted 认证与来源契约，可重复生成且 SHA-256 记录在本 Acceptance；禁止以手写平行 fixture 绕过依赖。
- 上述条件当前尚未满足，因此本 Plan 继续保持 `review`。

- [ ] 扩展既有 lint、typecheck、unit、build、E2E、a11y 和 OpenAPI diff 命令。

### 3.2 App Shell 与认证主体

- [ ] 在 Plan 000 的受保护 Server Component 外壳中增加最小 Client Component 来源工作台。

### 3.3 生成契约与幂等

- [ ] 仅从接受的 server OpenAPI 生成 transport types 与 MSW fixture。

### 3.5 媒体与清晰度

## 4. Red / Green 门禁

Red 必须由行为测试失败：未认证主体读取来源、false rights 仍发送、POST 缺失 CSRF 仍被执行、会话值进入 JavaScript 可读内容、URL 变化复用旧 key、SSE 丢事件、刷新新建 Job、错误码漂移、Variant 无键盘语义或 BFF 泄漏请求正文。

Green 必须证明 accepted 认证与来源 OpenAPI 的正负 fixture 均准确渲染；只有当前邮箱主体可恢复同一 Resolution；CSRF 负向请求被拒绝；只锁定 opaque key；完整键盘路径、响应式、泄漏扫描与性能验收通过。
