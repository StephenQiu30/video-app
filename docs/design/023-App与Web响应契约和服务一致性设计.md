# App 与 Web 响应契约和服务一致性设计

状态：Accepted。日期：2026-09-21。

## 问题结论

下载记录截图中的“暂时无法读取数据”不是后端离线。当前服务的 `/health/ready` 返回 200，Web 在相同服务和登录账户下可读取 75 条记录；失败发生在 App 客户端仍把业务响应当作直接模型解析，而服务端已将共享业务接口统一为 `{code, message, data}`。

Web 的 `request<T>` 在网络边界识别并解包统一响应，App 的冻结 OpenAPI 与生成客户端仍声明 `DownloadHistoryResponse` 为直接响应。Dio 收到 200 后因此在反序列化阶段失败，页面又把所有失败统一映射成网络错误，形成了错误诊断。

## 契约决策

- 服务端 OpenAPI 是共享业务接口的唯一事实来源；App 先更新冻结快照，再重新生成 `video_server_api`，不手改生成代码。
- 生成客户端保留真实 `ApiResponse*` 包装类型；各 Repository 在数据边界解包并校验 `data`，不通过拦截器篡改响应体，也不让 presentation 感知传输包装。
- `/api/app/v1/auth/*` 继续使用原生直接响应；不能因共享接口变更而给认证结果套用不存在的包装。
- 服务端错误统一读取 `code`、`message`、`data`；兼容旧 `detail` 只作为回退。认证、权限、限流、服务不可用和响应不合法必须保持不同的失败类型。
- `invalidResponse` 表示客户端与服务契约不匹配或数据缺失，UI 不得再提示用户检查网络。

## App 与 Web 服务边界

| 项目 | Web | App | 统一要求 |
| --- | --- | --- | --- |
| 认证 | 浏览器会话与同源请求 | Native Bearer 与安全存储 | 身份语义一致，凭据机制保持平台差异 |
| 成功响应 | `request<T>` 解包 `data` | 生成包装模型后由 Repository 解包 | 页面获得相同业务模型 |
| 错误响应 | 展示服务端可读错误 | `DataRequestFailure` 分类 | 使用相同 `code/message` 语义，不伪装为网络错误 |
| 下载历史 | 统计、搜索、筛选、分页、列表动作 | 相同业务能力的原生布局 | 数据、状态和动作一致；导航布局可不同 |
| 持久错误 | `PageErrorNotice` / `FeedbackNotice` | shadcn 语义状态组件 | 可见、可重试、可访问，且描述真实原因 |

## 视觉与交互审计

证据来自用户提供的 iPhone 17 Pro / iOS 27 截图和 2026-09-21 本地 Web `/history` 实际页面。

- App 已对齐标题、说明、搜索、状态筛选、主题入口和主导航；底部导航是移动端合理的平台差异。
- Web 成功态还包含“新建下载”、刷新、总数/完成/进行中摘要、封面列表、文件获取、删除和分页；App 当前错误态无法证明这些成功态能力。
- App 的错误区层级清晰、重试目标足够明显，但云断开图标和“检查网络连接”错误地把契约解析失败归因给网络；这是高优先级可信度问题。
- Web 的持久加载错误使用 `role=alert` 和 `aria-live`；App 修复后须用语义化状态组件并保留读屏标签，不能只换文案。
- 截图中的底部“历史”浮层像一次交互提示残留，不作为稳定页面组成；后续模拟器验收需确认其会自动消失且不遮挡导航。

## 非目标

- 不改为 WebView，不复用浏览器 Cookie，不建立第二套手写 DTO。
- 不在本次顺带修改 Provider、下载执行、对象存储或其他 `video-server` 工作区改动。
- 不以单元测试替代真实模拟器成功态和错误态检查。
